agent-demo 可观测架构

一个基于 OpenAI SDK 的 tool-calling Agent，内置面向 LLM 应用的完整可观测闭环：从业务埋点、OTLP 上报、Collector 采集分发，到 Trace / Metrics 存储，最终在 Grafana 统一展示。本文拆解系统架构，并追踪一条观测数据从产生到可视化的全链路与各阶段格式。

服务名 agent-demo 协议 OTLP gRPC :4317 维度 Trace + Metrics 部署 Docker Compose 语义约定 GenAI SemConv
01

系统总览架构

观测系统自下而上分为四层：应用层负责产生遥测数据，Collector 负责接收与分流，Tempo / Prometheus 分别存储 Trace 与 Metrics，Grafana 统一做查询与可视化，并支持 Trace 与指标之间的双向钻取。

观测数据：从采集到展示的全链路

追踪一次问答请求产生的遥测数据，依次经过五个阶段。每个阶段给出该阶段数据的真实格式示例，可以看到同一笔数据在 Trace 与 Metrics 两条管道中如何被打包、传输、存储与查询。

1

应用埋点 · 产生遥测数据

telemetry.py / agent.py

业务代码低侵入地创建 Span 与指标。根 Span invoke_agent 包裹整个回合；内部按 LLM 调用与工具调用再开子 Span，并写入 GenAI 语义约定属性。指标为 Counter / Histogram，异步周期上报。

埋点代码（agent.py）Python
# 一次问答的根 Span
agent_span = start_span("invoke_agent agent-demo", {
    "gen_ai.system": "openai",
    "gen_ai.request.model": model,
})
with start_span(f"chat {model}", ...):   # 子 Span：LLM 调用
    ...
    record_llm_duration(model, seconds)        # Histogram
    record_token_usage(model, in, out)         # Counter
with start_span(f"execute_tool calculator", ...):
    record_tool_call("calculator", "success")

OTLP 上报 · Collector 接收与批处理

gRPC :4317 · memory_limiter → batch

Trace 走 BatchSpanProcessor 异步批量导出；Metrics 走 PeriodicExportingMetricReader（默认 10s）。Collector 用 OTLP receiver 接收，经 memory_limiter 保护内存、batch 把多条数据聚合后再导出，减少网络往返。

otel-collector/config.yaml（精简）YAML
receivers:
  otlp:
    protocols: { grpc: {endpoint: "0.0.0.0:4317"} }
processors:
  memory_limiter: { limit_percentage: 75, spike_limit_percentage: 20 }
  batch: { send_batch_size: 1024, timeout: 5s }
service:
  pipelines:
    traces:  { receivers:[otlp], processors:[memory_limiter,batch],
               exporters:[otlp/tempo] }
    metrics: { receivers:[otlp], processors:[memory_limiter,batch],
               exporters:[prometheus] }
产出 · OTLP Metrics（ResourceMetrics）Metrics

分路导出 · Trace 与 Metrics 走向不同后端

tempo:4317 · prometheus :8889

Collector 按 pipeline 分流：Trace 通过 otlp/tempo exporter 直接以 OTLP gRPC 写入 Tempo；Metrics 通过 prometheus exporter 在 :8889 暴露 Prometheus exposition 格式，并开启 resource_to_telemetry_conversion 把 Resource 属性（如 service.name）转成指标 label。

存储与查询 · Tempo（TraceQL）/ Prometheus（PromQL）

Trace 1h · Metric 24h
Tempo · TraceQL 查询一次完整调用链TraceQL
# 在 Explore 中按服务名过滤，得到 trace 树
{ resource.service.name = "agent-demo" }

# 命中后返回的 Span 结构（按时间线展开）
○ invoke_agent agent-demo                 1.84s
├─ ● chat gpt-4o-mini                      0.62s  in=42 out=17
├─ ● execute_tool calculator               0.001s
└─ ● chat gpt-4o-mini                      1.21s  in=88 out=23

Tempo 以本地块文件存储，max_block_duration=5m、block_retention=1h。

Prometheus · PromQL 聚合查询PromQL
# 请求速率（按状态）
sum by(agent_status)(rate(agent_requests_total[5m]))

# LLM 延迟 p95
histogram_quantile(0.95,
  sum by(le)(rate(agent_llm_duration_seconds_bucket[5m])))

# 错误率（错误请求 / 全部请求）
sum(rate(agent_requests_total{agent_status="error"}[5m]))
  / clamp_min(sum(rate(agent_requests_total[5m])), 0.000001)

Prometheus 每 15s 抓取 Collector，TSDB 保留 24h。

5

展示 · Grafana 统一可视化与钻取

:3000 · Observability 仪表盘

Grafana 通过 Provisioning 自动挂载两个数据源：Prometheus（默认）渲染指标图表，Tempo 渲染 Trace。配置 tracesToMetrics 与 serviceMap 后，可从一条慢的 LLM 延迟曲线下钻到具体 Trace，也可从 Trace 跳回相关指标。

预置仪表盘面板：总请求数、错误率（>5% 标红）、LLM p95 延迟（>5s 橙 / >15s 红）、按状态请求速率、Token 消耗、工具调用分布。
Grafana 数据源关联配置（provisioning）YAML
- name: Tempo
  type: tempo
  url: http://tempo:3200
  jsonData:
    tracesToMetrics:
      datasourceUid: prometheus
    serviceMap:
      datasourceUid: prometheus
    nodeGraph: { enabled: true }

- name: Prometheus
  type: prometheus
  url: http://prometheus:9090
  isDefault: true
03

Trace 调用模型：一次问答的 Span 树

一次「带工具调用」的问答，在 Trace 中呈现为一棵三层 Span 树。根 Span 计时整轮耗时，子 Span 分别定位 LLM 与工具阶段；属性遵循 GenAI 语义约定，错误时写入 error.type。

ROOTinvoke_agent agent-demo
LLMchat gpt-4o-mini in=42 out=17
TOOLexecute_tool calculator status=success
LLMchat gpt-4o-mini in=88 out=23
→ 返回最终回答（无 tool_calls，循环结束）
父子关系通过 trace_id / span_id / parent_span_id 串联；FastAPI 入口另有自动产生的 http.server.request Span。
Span 名含义关键属性
invoke_agent agent-demo一次完整问答（根）gen_ai.request.model
chat <model>一次 LLM 调用usage.input/output_tokens
execute_tool <name>一次工具调用gen_ai.tool.name
http.server.requestHTTP 请求（自动）http.route / status_code

Metrics 指标清单

应用自定义四类指标，加上 FastAPI 自动埋点的 HTTP 指标。Prometheus 中 Counter 自动追加 _total 后缀，Histogram 生成 _bucket / _sum / _count。

指标名类型标签维度含义
agent.requestsCounteragent.status问答请求总数（success / error）
agent.tokensCountertoken.type, gen_ai.request.modelLLM token 消耗（input / output）
agent.llm.durationHistogramgen_ai.request.modelLLM 调用耗时（秒）
agent.tool.callsCountergen_ai.tool.name, tool.status工具调用次数与成功率
http.server.*自动route, method, statusFastAPI HTTP 请求量 / 延迟

一条命令拉起五个服务；也可用 docker-compose.infra.yml 只起监控栈，应用在宿主机运行并上报到 localhost:4317。

设计取舍与边界

本期已实现

  • · Trace + Metrics 覆盖 Agent 全链路
  • · 遵循 OTel GenAI 语义约定，后端可替换
  • · 低侵入、可一键关闭，无后端不影响主流程
  • · Collector 统一接入，应用不直接暴露指标

MVP 边界（暂不做）

  • · 不做 Logs / Loki 日志采集
  • · 不做告警规则与通知
  • · 单实例本地存储，非生产高可用
  • · 不采集 Prompt / Completion 正文，规避隐私风险
