OpenTelemetry · Tempo · Prometheus · Loki · Grafana

agent-demo 可观测架构

一个基于 OpenAI SDK 的 tool-calling Agent，内置面向 LLM 应用的完整可观测闭环：从业务埋点、OTLP 上报、Collector 采集分发，到 Trace / Metrics / Logs 三类遥测分别落地 Tempo / Prometheus / Loki，最终在 Grafana 统一展示。本文拆解系统架构，并追踪一条观测数据从产生到可视化的全链路与各阶段格式。

服务名 agent-demo 协议 OTLP gRPC :4317 维度 Trace + Metrics + Logs 部署 Docker Compose 语义约定 GenAI SemConv 扩展 opencode 多租户平台（第 07 节）
01

系统总览架构

观测系统自下而上分为四层：应用层负责产生遥测数据，Collector 负责接收与分流，Tempo / Prometheus / Loki 分别存储 Trace / Metrics / Logs，Grafana 统一做查询与可视化，并支持 Trace ↔ Metrics ↔ Logs 之间的关联钻取。

观测数据：从采集到展示的全链路

应用埋点 · 产生遥测数据

telemetry.py / agent.py

业务代码低侵入地创建 Span、指标与日志。根 Span invoke_agent 包裹整个回合；内部按 LLM 调用与工具调用再开子 Span，并写入 GenAI 语义约定属性。指标为 Counter / Histogram，异步周期上报；业务日志用标准 logging 输出，自动附带 trace_id。

埋点代码（agent.py）Python
# 一次问答的根 Span
agent_span = start_span("invoke_agent agent-demo", {
    "gen_ai.system": "openai",
    "gen_ai.request.model": model,
})
with start_span(f"chat {model}", ...):   # 子 Span：LLM 调用
    ...
    record_llm_duration(model, seconds)        # Histogram
    record_token_usage(model, in, out)         # Counter
    logger.info("LLM 调用完成 model=%s 耗时=%.2fs ...", ...)
with start_span(f"execute_tool calculator", ...):
    record_tool_call("calculator", "success")
    logger.info("工具执行成功 name=%s 结果=%s", ...)

OTLP 上报 · Collector 接收与批处理

gRPC :4317 · memory_limiter → batch

Trace 走 BatchSpanProcessor 异步批量导出；Metrics 走 PeriodicExportingMetricReader（默认 10s）；Logs 走 BatchLogRecordProcessor，通过 LoggingHandler 挂到根 Logger——业务代码用标准 logging 即可上报。Collector 用 OTLP receiver 接收，经 memory_limiter 保护内存、batch 聚合后按三条 pipeline 分流导出。

otel-collector/config.yaml（精简）YAML
receivers:
  otlp:
    protocols: { grpc: {endpoint: "0.0.0.0:4317"} }
processors:
  memory_limiter: { limit_percentage: 75, spike_limit_percentage: 20 }
  batch: { send_batch_size: 1024, timeout: 5s }
exporters:
  loki: { endpoint: "http://loki:3100/loki/api/v1/push" }
service:
  pipelines:
    traces:  { receivers:[otlp], processors:[memory_limiter,batch],
               exporters:[otlp/tempo] }
    metrics: { receivers:[otlp], processors:[memory_limiter,batch],
               exporters:[prometheus] }
    logs:    { receivers:[otlp], processors:[memory_limiter,batch],
               exporters:[loki] }

分路导出 · Trace / Metrics / Logs 走向不同后端

tempo:4317 · prometheus :8889 · loki :3100

Collector 按 pipeline 分流：Trace 通过 otlp/tempo exporter 直接以 OTLP gRPC 写入 Tempo；Metrics 通过 prometheus exporter 在 :8889 暴露 Prometheus exposition 格式，并开启 resource_to_telemetry_conversion 把 Resource 属性（如 service.name）转成指标 label；Logs 通过 loki exporter 以 HTTP POST 写入 Loki push API，Resource 属性转为 Loki 流标签（service.name → service_name），日志行内保留 trace_id=xxx 文本用于关联。

存储与查询 · Tempo（TraceQL）/ Prometheus（PromQL）/ Loki（LogQL）

Trace 1h · Metric 24h · Log 24h
Tempo · TraceQL 查询一次完整调用链TraceQL
# 在 Explore 中按服务名过滤，得到 trace 树
{ resource.service.name = "agent-demo" }

# 命中后返回的 Span 结构（按时间线展开）
○ invoke_agent agent-demo                 1.84s
├─ ● chat gpt-4o-mini                      0.62s  in=42 out=17
├─ ● execute_tool calculator               0.001s
└─ ● chat gpt-4o-mini                      1.21s  in=88 out=23

Tempo 以本地块文件存储，max_block_duration=5m、block_retention=1h。

Loki · LogQL 检索业务日志LogQL
# 按服务名查全部日志（标签由 Resource 转换而来）
{service_name="agent-demo"}

# 只看错误日志 / 检索关键字
{service_name="agent-demo"} |= "工具执行失败"

# 日志总量速率
sum(rate({service_name="agent-demo"}[5m]))

Loki 为 TSDB 索引 + 文件系统 chunks，retention_period=24h。

Prometheus · PromQL 聚合查询PromQL
# 请求速率（按状态）
sum by(agent_status)(rate(agent_requests_total[5m]))

# LLM 延迟 p95
histogram_quantile(0.95,
  sum by(le)(rate(agent_llm_duration_seconds_bucket[5m])))

# 错误率（错误请求 / 全部请求）
sum(rate(agent_requests_total{agent_status="error"}[5m]))
  / clamp_min(sum(rate(agent_requests_total[5m])), 0.000001)

Prometheus 每 15s 抓取 Collector，TSDB 保留 24h。

5

展示 · Grafana 统一可视化与钻取

:3000 · Observability 仪表盘

Grafana 通过 Provisioning 自动挂载三个数据源：Prometheus（默认）渲染指标图表，Tempo 渲染 Trace，Loki 渲染日志。配置 tracesToMetrics 与 serviceMap 后，可从一条慢的 LLM 延迟曲线下钻到具体 Trace；Loki 数据源开启 derivedFields 后，日志行中的 trace_id=xxx 渲染为「查看 Trace」链接，点击即跳转到 Tempo 对应 Trace——实现 Logs → Trace 的故障排查闭环。

预置仪表盘面板：总请求数、错误率（>5% 标红）、LLM p95 延迟（>5s 橙 / >15s 红）、按状态请求速率、Token 消耗、工具调用分布、应用日志（Loki）（日志行内 trace_id 可点击跳转）。
Grafana 数据源关联配置（provisioning）YAML
- name: Tempo
  type: tempo
  url: http://tempo:3200
  jsonData:
    tracesToMetrics:
      datasourceUid: prometheus
    serviceMap:
      datasourceUid: prometheus
    nodeGraph: { enabled: true }

- name: Loki
  type: loki
  url: http://loki:3100
  jsonData:
    maxLines: 1000
    derivedFields:
      # 日志行 trace_id=xxx → 可点击跳转 Tempo
      - matcherRegex: "trace_id=([0-9a-fA-F]+)"
        datasourceUid: tempo

- name: Prometheus
  type: prometheus
  url: http://prometheus:9090
  isDefault: true
03

Trace 调用模型：一次问答的 Span 树

一次「带工具调用」的问答，在 Trace 中呈现为一棵三层 Span 树。根 Span 计时整轮耗时，子 Span 分别定位 LLM 与工具阶段；属性遵循 GenAI 语义约定，错误时写入 error.type。

ROOTinvoke_agent agent-demo
LLMchat gpt-4o-mini in=42 out=17
TOOLexecute_tool calculator status=success
LLMchat gpt-4o-mini in=88 out=23
→ 返回最终回答（无 tool_calls，循环结束）
父子关系通过 trace_id / span_id / parent_span_id 串联；FastAPI 入口另有自动产生的 http.server.request Span。业务日志经 OTel LoggingHandler 自动附加当前 Span 的 trace_id，且 Web 层日志显式写入 trace_id=xxx，因此每条日志都能在 Loki 中点击跳转到 Tempo。
Span 名含义关键属性
invoke_agent agent-demo一次完整问答（根）gen_ai.request.model
chat <model>一次 LLM 调用usage.input/output_tokens
execute_tool <name>一次工具调用gen_ai.tool.name
http.server.requestHTTP 请求（自动）http.route / status_code

06

设计取舍与边界

本期已实现

  • · Trace + Metrics + Logs 覆盖 Agent 全链路（Logs 经 OTLP 写入 Loki）
  • · 日志与 Trace 关联：日志行含 trace_id，可一键跳转 Tempo
  • · 遵循 OTel GenAI 语义约定，后端可替换
  • · 低侵入、可一键关闭，无后端不影响主流程
  • · Collector 统一接入，应用不直接暴露指标

MVP 边界（暂不做）

  • · 不做告警规则与通知
  • · 单实例本地存储，非生产高可用（Trace 1h / Metric 24h / Log 24h）
  • · 不采集 Prompt / Completion 正文，规避隐私风险
  • · 未使用 OTel auto-instrumentation，埋点手写以贴合 Agent 语义
07

扩展场景：多容器多租户 opencode Agent 平台

前六节描述单体 agent-demo；本节外推到更接近生产的形态——平台为每个租户 / 每个会话动态拉起独立的 opencode 容器，Agent 实例通过 OpenTelemetry 插件（opencode-otel）统一接入本方案的 Tempo / Prometheus / Loki 监控栈，监控侧做四方面适配：采集层弹性、租户身份标准化、存储隔离与容量、展示隔离。

图 2 · 多容器多租户 opencode Agent 平台的接入拓扑（平台容器 → Collector 多副本 → 三后端 → Grafana 租户视图）

Agent 侧 · opencode-otel 插件接入

opencode-otel（npm v1.2.1+）拦截 opencode 进程 stderr，按 ERROR/WARN/INFO/DEBUG 前缀解析级别封装为 OTLP LogRecord 批量导出（stderr 原样保留），并支持可选的会话关联 Trace（仅 gRPC）；未使用的 metrics 环境变量被安全忽略。插件未配置日志端点时保持不激活。

opencode.json（打进容器镜像）JSON
{
  "plugin": ["opencode-otel"]
}
平台拉起容器时按租户注入Env
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://otel-collector:4317
OTEL_EXPORTER_OTLP_LOGS_PROTOCOL=grpc
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://otel-collector:4317
OTEL_EXPORTER_OTLP_TIMEOUT=2000
# 租户身份：service.name 按租户命名
OTEL_RESOURCE_ATTRIBUTES=service.name=opencode-tenantA,\
  service.namespace=agent-platform,\
  tenant.id=tenantA,session.id=s-20260927-001,\
  host.name=$(hostname)
OTEL_SERVICE_NAME=opencode-tenantA
多租户部署可用 OTEL_PLUGIN_CONFIG_PATH 指向每容器专属 otel.json（env 优先）。需要「会话 → 消息 → 工具调用」完整 Span 树时，可按 @opencode-ai/plugin 自研插件，在 session.created / tool.execute.* / session.error 等钩子中建 Span，复用同一租户身份。

监控侧 · Collector 多租户适配

采集层升级三件事：横向弹性（多副本 + LB，sending_queue/retry 抗后端抖动）、身份标准化（resourcedetection 补容器身份，resource 处理器归一化租户字段）、规模治理（tail_sampling 采样、filter 控基数）。

otel-collector/config.yaml（增量）YAML
processors:
  resourcedetection:
    detectors: [env, system, docker]
  resource/tenant:
    attributes:
      - key: service.namespace
        value: agent-platform
        action: upsert
  memory_limiter:
    { check_interval: 1s, limit_percentage: 75 }
  batch: { send_batch_size: 2048, timeout: 5s }

exporters:
  otlp/tempo:
    endpoint: tempo:4317
    sending_queue: { enabled: true }
    retry_on_failure: { enabled: true }

# 三条 pipeline 均插入 resourcedetection 与
# resource/tenant；traces 可再加 tail_sampling
三类信号统一携带 tenant.id / session.id；Metrics 开启 resource_to_telemetry_conversion 后按 tenant_id 聚合，Logs 转为流标签 tenant_id，Trace 用 TraceQL 属性检索。
后端单体默认（第 05 节）多租户适配
Tempo 保留 1h，单租户 保留 24h~7d；多租户两路线：① OrgID 真隔离（multitenant_enabled + X-Scope-OrgID，需 per-tenant exporter / routing connector）；② 属性检索（单租户模式，TraceQL { resource.tenant.id="tenantA" }，部署简单隔离弱）
Prometheus 保留 24h 保留 7~30d + retention.size 控盘；tenant_id 成为普通 label，警惕基数膨胀（租户×实例×指标×标签）；Recording Rules 预聚合按租户关键指标；更大规模按租户分片
Loki 单租户，保留 24h 推荐 auth_enabled: true + X-Scope-OrgID 真隔离（routing connector 或 Loki 原生 OTLP 端点按租户写入）；或单租户模式以 tenant_id 为流标签（流基数 = 租户×服务×级别，可控），配 per-tenant 限流
Grafana 匿名 Admin 单空间 按租户 Folder + Team 权限隔离；仪表盘顶部 $tenant / $session 模板变量；多租户后端需在数据源配置 httpHeader: X-Scope-OrgID；大型场景按租户拆组织 / 实例
容量粗估：Loki 磁盘 ≈ 每容器日志量 × 并发容器数 × 保留天数；指标基数先灰度 1~2 个租户观测 cardinality 再全量放开；Trace 采样率按「错误/慢请求全保留，其余抽样」折中成本。
生产演进：编排上 k8s（HPA + 每租户 ResourceQuota）；Collector Deployment 多副本；Tempo / Loki 存储换对象存储（S3 后端）支撑长保留期；配额、保留期、告警按租户策略配置。Docker Compose 下仅需第 05 节基础 + 上述增量配置 + platform-gateway 服务。
